## 1. Plan-editor save can destroy logged sets, with no undo

**Severity HIGH · Effort S · Risk LOW**

Evidence:
- `js/block-editor.js:975` — `peDraftOriginalDay[ex.id] = day.id` is keyed by
  exercise id alone. A block carrying the same id on two days (which
  `migrate()` allows on purpose — `js/app.js:303-309` dedupes within a day
  only, and `test/unit.js:226` asserts "the same id on two different days
  survives, by design") leaves the map pointing at whichever day was walked
  last.
- `js/block-editor.js:1002-1007` — on **Guardar cambios**, every exercise
  whose current day differs from that map entry calls `moveExLog`, even when
  nothing was moved.
- `js/app.js:1455-1466` — `moveExLog` does `blk[toKey][exId] = from[exId]`
  and deletes the source: the destination day's own rows for that id are
  overwritten, not merged.
- `js/block-editor.js:996-1019` — the save handler never calls
  `snapshotForUndo`, unlike `deleteBlocks` (`:74`), clearing a day
  (`js/app.js:2735`) and wiping a profile (`:2751`). It is the one save path
  that can erase rows, and it has no undo.

Failure scenario: a profile restored from an older backup, or hand-edited,
has `chestpress` on day A and day B with sets logged on both. The user opens
**Editar plan**, changes nothing, taps **Guardar cambios**. Day A's chest
press history is replaced by day B's and day B's is deleted. The status line
says "el registro se mantiene". There is no undo.

Plan:
1. Track the origin by object identity: build `peDraftOriginalDay` as a
   `Map` from the draft exercise object to its original day id. "Enviar a"
   moves the object between draft days (`moveExToDay`, `:515`), so identity
   survives; the id-only lookup goes away.
2. Make `moveExLog` merge rather than overwrite when the destination already
   has rows for the id (append, or refuse and report). With step 1 the
   spurious call no longer happens, but the function should still not be
   able to destroy data if called twice.
3. Call `snapshotForUndo('Plan actualizado.')` at the top of the `peSave`
   handler, before the move/purge loops, so the existing one-level undo
   covers it.
4. Unit test: a block with `e1` on two days, rows on both, build the draft
   state the way `editPlan.onclick` does and run the save loop; assert both
   days' rows survive. Smoke test: open and save the editor on such a
   block, assert the undo toast appears.

STOP if: the README's "same lift on two days" section (line 491) turns out
to rely on the id-only map. It does not appear to — `sameLift`
(`js/app.js:1515`) matches by id or name and never reads the draft map —
but check before changing the key.

## 2. A `__proto__` id in an imported block sends the user to the recovery screen

**Severity HIGH · Effort S · Risk LOW**

Evidence (reproduced in the unit harness):
- `js/block-editor.js:231` — `baseId = txt(e.id, 60) || …`. `txt()`
  (`js/app.js:2075`) trims and caps; it never rejects `__proto__`,
  `constructor` or `prototype`. The id survives normalization unchanged.
- `js/app.js:1038-1044` — `rowsFor` does `if (!log[k][exId]) log[k][exId] = []`
  on a plain `{}`. For `exId === '__proto__'` the read returns
  `Object.prototype` (truthy), nothing is assigned, and `Object.prototype`
  is returned as "the rows".
- `js/app.js:1046-1048` — `entry()` then calls `a.push` on it: `TypeError`.
- `js/app.js:2124-2131` — `render()` catches the throw and calls
  `showRecovery`, which freezes writes (`:903-905`) and shows "No se ha
  podido abrir tu registro".
- `js/block-editor.js:334-345` — the import calls `save(); render()` and then
  `flushSave()`. Because recovery clears the pending timer first, nothing is
  persisted: a reload brings the old state back. Data-safe, but the user
  has just been told their log is broken and to download it before anything
  else.
- `js/profile-transfer.js:64-80` — the same key used as a **block id** in a
  restored backup (`blocks[bk] = normalized`) sets the prototype instead of
  a property; the block silently disappears from `Object.keys(blocks)`.

Failure scenario: paste a block JSON whose exercise has `"id": "__proto__"`
(or scan one by QR, or import one from a fork's `blocks/`). The app drops to
the recovery screen.

Plan:
1. Add one helper next to `txt()`: `safeKey(s)` returning `''` for
   `__proto__`, `constructor`, `prototype` (`Object.prototype.hasOwnProperty.call({}, s)`
   is not enough on its own since `{}` owns nothing; test against a fixed
   deny-list), and use it in `normalizeImportedBlock` for exercise ids
   (`:231`) and day ids, in `normalizeImportedProfile` for block keys
   (`:65`), and in `migrate()` where ids are accepted from storage
   (`js/app.js:291`, `:305`).
2. The id-keyed maps (`log`, `rir`, `notes`, `energy`, `order`) could be
   created with `Object.create(null)` the way `renderCache` already is
   (`:2183`), but `JSON.parse` hands back ordinary objects on load, so step
   1 is the fix and this is belt-and-braces.
3. Unit tests: `normalizeImportedBlock` with a `__proto__` exercise id yields
   a slug id; `normalizeImportedProfile` with a `__proto__` block key
   renames or rejects it; `rowsFor` on such ids returns a real array.

## 3. "Enviar a otra sesión" strands the exercise's RIR and set-order history

**Severity HIGH · Effort S · Risk LOW**

Evidence:
- `js/app.js:1103-1114` — `profile.rir` is documented as "a parallel map with
  the same blockId → slot → exId shape" as the log, and `getRir` reads it by
  the exercise's *current* day.
- `js/block-editor.js:1002-1007` — the save handler moves only `profile.log`
  via `moveExLog`. There is no `moveExRir` / `moveExOrder` anywhere (grep).
- `profile.order` (`js/app.js:~1219-1230`) is keyed by slot with exercise ids
  as values, so the old day's order array keeps naming the moved exercise and
  the new day's never gains it.

Why HIGH rather than MEDIUM: the weekly *objetivo* is computed from last
week's reps **and RIR** (README, "The weekly objetivo"; PR #59). Losing the
RIR chips after a legitimate move silently degrades every target for that
exercise for the rest of the block, and the chips are gone from the UI with
no message.

Plan:
1. Generalise `moveExLog` into `moveExKeyed(map, blockId, from, to, exId)`
   and call it for `log`, `rir` and `notes` if `notes` is keyed the same
   (check `getNote`); write a small `moveExOrder` that removes the id from
   the source slot's array and appends it to the destination's.
2. Call all of them where `moveExLog` is called today.
3. Unit test: move an exercise with a RIR chip and an order entry, assert
   `getRir` on the new day returns it and the old slot is clean.

**Depends on:** 1 (same code path; land together or 1 first).

## 4. Backup and profile-file restore skip the per-row log validation the QR path has

**Severity HIGH · Effort M · Risk MED**

Evidence:
- `js/app.js:4141`, `:4492`, `:4532` — the QR "blocklog" path runs every row
  through `normalizeImportedLog` / `normalizeImportedRir` under `LOG_LIMITS`
  (24 rows per exercise, 12-char values, RIR restricted to `RIR_OPTIONS`).
- `js/profile-transfer.js:102-106` — `normalizeImportedProfile` only deletes
  `log`/`rir`/`notes`/`energy`/`order` entries whose block id no longer
  exists. Row arrays, value lengths and enum membership are never checked.
- `js/app.js:225-248` — `migrate()` never descends into `log`/`rir`/
  `notes`/`energy` either (only `order` is sanitised per value).
- Consumers that iterate whole row arrays rather than `entry()`'s slice:
  `countProfileSets` (`profile-transfer.js:112`), `blockShareLog`,
  `blockTonnageByWeek`, the CSV export (`js/app.js:4936-4954`), the volume
  dashboard's `Math.max(...)` spreads (`:3708-3760`).

Failure scenario: a backup file with one exercise's row array padded to a
few million entries restores without complaint (`describeBackupProblem`
passes), and the first tap on **Volumen muscular** or **Exportar CSV** hangs
the tab. Less adversarially: a partner's hand-repaired file with `"rir":
"3"` restores a value no chip can display and no arithmetic can read.

Plan:
1. Lift `normalizeImportedLog` / `normalizeImportedRir` (and `LOG_LIMITS`)
   out of the QR section into the shared helpers block (`js/app.js:2009`,
   next to `IMPORT_LIMITS`) — they are already called across the file
   boundary, so this is a move, not a change.
2. In `normalizeImportedProfile`, after the block loop, run each block's
   `log`/`rir` through them and cap `notes`/`energy` values with `txt()` and
   the energy enum. Reject (throw with the Spanish message the sheet
   already shows) rather than truncate when a row array exceeds the limit
   by more than a sane margin, matching how `ex.add` is handled.
3. Consider the same pass in `migrate()` for stored data, but note the
   trade-off the recovery-screen comment makes (`js/app.js:110-116`):
   repair, never discard. Truncating a stored row array to `LOG_LIMITS.rows`
   is repair; deleting a slot is not.
4. Unit tests: oversized row array rejected; bad RIR dropped; the restore
   happy path in `test/smoke.js:977-993` still passes.

## 5. Solo mode moves the second person onto the first person's log

**Severity MEDIUM · Effort S · Risk LOW**

Evidence:
- `js/app.js:687-691` — `setupDraft.people` is `profileKeys()` in insertion
  order.
- `:753` — in solo mode only `people[0]` gets a name box; `:825` —
  `state.activeProfile = setupDraft.people[0].key`.

Failure scenario: the second profile is active. They open **Ajustes**, turn
on "Solo yo", type their name. The name lands on the *first* profile's
label and they are switched onto its blocks and log. Their own history is
still there (solo hides, it never deletes) but from where they are standing

Plan: order `setupDraft.people` with the active profile first (one `sort` or

index. Smoke test: activate profile 2, enable solo, assert the title shows
their name and their block.

## 6. Two same-device hangs from unbounded numbers: `fitPlates` and `qrInflate`

**Severity MEDIUM · Effort S · Risk LOW**

- `js/app.js:350`, `:820` — plates are only filtered with `p > 0`;
  `fitPlates` (`:3441-3450`) loops `while (remaining - p > -1e-6)` per plate,
  so a `0.0001` plate typed into Ajustes (or restored from a backup) costs
  `target / 0.0001` iterations and array pushes on the next **Calculadora**
  open. Fix: clamp plates to `[PLATE_MIN, PLATE_MAX]` (e.g. 0.25–50 kg /
  0.5–100 lb) in `migrate()` and the setup save, and cap `used.length` in
  `fitPlates` as a second line.
- `js/app.js:4206-4211` — `qrInflate` decompresses the whole stream into
  memory before any shape check. Input is bounded to ~16 KB compressed
  (`QR_MAX_FRAMES × QR_CHUNK`), so the exposure is a ~1000× expansion on a
  phone, not unbounded — but it is camera input from a screen someone else
  controls. Fix: read `ds.readable` with a reader, accumulate against a
  budget (a few MB is generous for any real profile), and throw past it.

Unit tests for both are cheap and belong in `test/unit.js`.

## 7. Published blocks are fetched cross-origin, so the worker's offline fallback for `blocks/` never runs

**Severity MEDIUM · Effort S · Risk MED**

Evidence:
- `sw.js:8-10`, `:141-144` — the worker promises "a block you have already
  seen should still be importable offline" and serves `/blocks/`
  network-first with a cache fallback — **for same-origin requests only**
  (`sameOrigin && url.pathname.indexOf('/blocks/') >= 0`).
- `js/app.js:2015-2027` — `blocksBase()` always returns a
  `raw.githubusercontent.com` URL, and `js/block-editor.js:352`, `:371`,
  `:445`, `:465` fetch from it with `cache: 'no-store'`. Cross-origin, so
  the worker's `fetch` handler falls through (`sw.js:146-153` handles only
  same-origin and Google Fonts). Offline, every block import fails; the
  handler and its comment are dead in production.
- `.github/workflows/pages.yml:30` uploads `.` — `blocks/` is already
  deployed on the same origin as the app.

Plan (pick one; the first is simpler and shrinks the CSP):
- **A.** Fetch `blocks/…` relative to the page. Same-origin means the
  existing handler works as documented, `connect-src` can drop
  `raw.githubusercontent.com` (`index.html:9`), and the fork-detection code
  in `blocksBase()` goes away (a fork serving its own Pages already serves
  its own `blocks/`). Cost: a block pushed to `main` shows up after the
  Pages deploy rather than instantly — the deploy runs on every push, so
  that is minutes, and the same delay the app itself has.
- **B.** Keep the URL and add a `raw.githubusercontent.com` branch to the
  worker that caches into `RUNTIME_CACHE`. Keeps instant publishing, keeps
  the CSP entry, and the `cache: 'no-store'` option must go or the worker
  never sees a cacheable response.

Either way, update the `sw.js` header comment and add a smoke case that
imports a block, goes offline (`context.setOffline(true)`) and imports it
again.

## 8. Backups cannot be saved from an installed iOS app

**Severity MEDIUM · Effort S · Risk LOW**

`js/app.js:938-948` — `downloadFile` uses `<a download>` on a blob URL. In
an iOS home-screen PWA (`apple-mobile-web-app-capable`, `index.html:15`)
that path is unreliable: there is no browser chrome to complete a
download, and depending on the iOS version the tap does nothing or opens
the blob in place with no way to save it. This is the backup path the app
nags about after ten sessions (`:3914-3923`), on the platform the icons
were specifically added for. Not documented in "Known limits".

Plan: when `navigator.canShare && navigator.canShare({ files: [file] })`,
call `navigator.share({ files: [new File([blob], name)] })` first and fall
back to the anchor; on failure, show the JSON in a textarea with a "Copiar"
button (the QR sheet already has clipboard code). Add the limitation to
the README until it lands. Same change fixes CSV and profile-file export.

## 9. Diagnostics and the block review blend kg and lb history after a unit switch

**Severity MEDIUM · Effort M · Risk LOW**

`js/app.js:334-346` decides that the unit is "a label, never a conversion"
and stored numbers are never rescaled — a sound choice for the session
view. But `diagPoints`/`fitSlope`/`est1RM` (`js/diagnostics.js:87-90`,
`:347`, `:461-469`) and `reviewText`'s tonnage (`js/review.js:134`, `:167`)
fit one line through every stored number and label it with the *current*
unit. A switch mid-block (or a backup restored from a partner who uses the
other unit) produces a +120% "trend" and a review brief that hands the next
block's writer numbers in the wrong unit, with no warning anywhere.

Plan: stamp the unit on each row when it is written (`u: 'lb'` only when it
differs from kg, the way `share`/`ss` are stored only when true), and have
the diagnostics and review either convert to the display unit or exclude
and flag rows in the other unit. This is also the prerequisite for item
19's unit-safe features. Do not convert stored numbers in place.

## 10. The worker can activate with a hole in the precached shell

**Severity MEDIUM · Effort S · Risk LOW**

`sw.js:48-55` — every `cache.add` failure is swallowed so one miss does not
fail the install. The consequence: a flaky first install activates and
claims clients with, say, `js/diagnostics.js` missing from the cache. The
app then reports itself installed; offline, that script 404s and the
`typeof wireDiagnostics` guard (`js/app.js:4989`) hides the button — the
right failure — but nothing ever retries, so the hole persists until the
next `CACHE_VERSION`.

Plan: keep the tolerant install, and on `activate` (and on the
`visibilitychange` update check) re-`add` any `SHELL` entry `cache.match`
does not find. Ten lines. While there, give `js/vendor/` its own
`VENDOR_CACHE` keyed on a separate version so the 318 KB of QR libraries
stop being re-fetched on every one of the ~45 bumps so far. Smoke test
with a route that fails one shell file on first load.

## 11. Wake lock leaked when a rest is skipped mid-request

**Severity LOW · Effort S · Risk LOW**

`js/app.js:1928-1936` — `requestWakeLock` awaits `navigator.wakeLock.request`
and assigns the result unconditionally; `stopRest` (`:1630-1637`) calls
`releaseWakeLock` synchronously. Tapping **Saltar** inside the request's
latency leaves a lock held with no timer. Fix: after the `await`, if `tId`
is null, release immediately instead of assigning.

## 12. Heat-map week count is DST-fragile

**Severity LOW · Effort S · Risk LOW**

`js/diagnostics.js:270` — `weeks = floor((last - first) / (7·86400000)) + 1`
on local-midnight dates. Across a DST change a week measures 167 or 169
hours, so a span landing on a boundary loses or gains a column; the loop
below already does DST-safe calendar arithmetic. Fix: count calendar days
via `Date.UTC(y, m, d)` on both ends.

## 13. CI hardening

**Severity MEDIUM (security) · Effort S · Risk LOW**

All in `.github/workflows/`; none change app behaviour.

1. `test.yml` has no `permissions:` block, so both jobs get the default
   `GITHUB_TOKEN` scopes while running freshly-resolved npm code. Add
   `permissions: contents: read` at the top.
2. `test.yml:56` interpolates `${{ github.base_ref }}` straight into a
   `run:` script. Move it to `env:` and read `$BASE_REF`.
3. `pages.yml:25-34` pins actions to mutable major tags while holding
   `pages: write` and `id-token: write`. Pin to commit SHAs (Dependabot can
   keep them fresh with a two-line `.github/dependabot.yml`).
4. `js/vendor/README.md` records sha256 digests that nothing checks. Add a
   step (`sha256sum -c` against a checked-in `js/vendor/SHA256SUMS`). The
   digests currently match. `.gitattributes` already forces LF, so the
   check is stable on Windows checkouts.
5. The `cache-version` job checks the bump but not the `SHELL` array. Add a
   step that greps every `js/*.js` and `css/*.css` path out of `sw.js`'s
   `SHELL` and fails on a file missing from it — the half AGENTS.md says
   "is on you".
6. `js/data.js:6-9` asks whoever edits the seed plans to regenerate
   `blocks/hombre-bloque-1.json` and `blocks/mujer-bloque-1.json` by hand.
   They are in sync today (checked programmatically). A ten-line
   `test/unit.js` case comparing `DEFAULT_DAYS_TU/PAREJA` to the two files
   turns the comment into a check.
7. Chromium is downloaded on every PR. `actions/cache` keyed on the pinned
   Playwright version (`~/.cache/ms-playwright`) saves 1.5–2.5 min per run.

## 15. Stop rebuilding the whole session on every set tick

**Severity MEDIUM (performance) · Effort M · Risk MED**

`js/app.js:2450-2456` — every tick calls `render()`, which rebuilds the
entire day (≈400 nodes, ≈160 handlers for a seven-exercise day) on the
app's most frequent interaction. Two workarounds exist only because of it:
the `data-drop-focus` marker (`:2556`) and the focus/`setSelectionRange`
restore for the machine-settings box (`:2397-2398`). Plan 005 removed the redundant scans, which was the
prerequisite.

Plan: give each card a `data-ex` attribute and a `drawCard(ex)` that
replaces just that card; keep the full `render()` for navigation. The tick
handler also updates tonnage, the PR badge, the progress bar and the
day-complete nag — list them first and update each explicitly, and keep
the smoke assertions that cover them (`test/smoke.js` "tick / timer /
tonnage") as the gate.

## 18. Accessibility and CSP

**Severity LOW · Effort S · Risk LOW**

- `index.html:472` — the toast (undo, update prompt) is not a live region;

## 19. Features worth adding

Each is small, and each is a gap a user of the app hits, with evidence in
the code that it is not already handled.

- **Bodyweight and assisted exercises.** `js/diagnostics.js:87` needs
  `w > 0` for a session to count, so pull-ups or dips logged at 0 never
  produce a point and show the same "Aún no hay suficientes sesiones" as an
  empty exercise (`:591-592`). Add a `bw: true` flag in the plan editor
  meaning "weight is added load, may be 0 or negative for assistance", and
  treat e1RM as body-weight-plus-load (ask for body weight once in
  Ajustes). Until then, at least give the zero-weight case its own message.
- **Unit stamped per row** (item 9) — the enabler for a safe unit switch
  and for importing a partner's profile in the other unit.
- **Share-sheet export** (item 8) — the fix and the feature are the same
  change: `navigator.share` with a file is how iOS users expect to hand a
  backup to Files or a chat.
- **A visible "última copia" date in Ajustes** next to the backup button:
  `sessionsSinceBackup` already tracks it (`js/app.js:358`, `:2466`); showing the
  date turns the nag into information.
